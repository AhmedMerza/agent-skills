# Agent skill routing

Use the skills installed from `agent-skills` when the task reaches their trigger. Say which skill you are applying and why. The skill is a procedure to follow, not just a label to mention. Read its `SKILL.md` before acting. An explicit user request for a skill takes priority; do not force every task through the entire chain.

- Whenever you are about to ask the user to choose between approaches: `best-option` first. Explain each option, check for a better unlisted one, lead with your pick marked "(Recommended)", and say why the others lose.
- An unclear idea or problem with no route: `scout` to settle the destination and decisions. For a reported bug that needs diagnosis: `root-cause`. If a plan already exists and its assumptions matter: `validate-plan` before implementation.
- Product work: when anything end users touch is being planned, use `expand` in light mode on your own initiative (at most three ideas, offered at a boundary, never mid-implementation). Use full mode, with its own competitor research, at a product kickoff or milestone boundary. `scout` calls it for product destinations.
- A roadmap or multi-step plan is ready: `grill-me` with the user (scout and lead hand off to it at the roadmap gate), then `validate-plan` before filing issues or starting work.
- During implementation: `ponytail` for minimal, grounded code. When a new regression test matters: `prove-the-test`. For a changed UI flow, before committing: `qa-sweep` checks failures, and `persona-walkthrough` tests whether a first-time human can understand and finish the flow (when a runnable app is available).
- For every PR/MR with user-visible UI changes, capture before and after screenshots of the affected screen and state, embed them in the PR/MR description (or a linked comment), and verify they render for reviewers. Do this before marking it ready; refresh them after later UI changes. A local screenshot path or private artifact link does not count. If capture is blocked, keep the PR/MR draft and explain the blocker; do not merge it without the images. A new screen's before image may show its previous entry point or absence, clearly labeled.
- Review chain, once the PR/MR is open and the question is whether to merge it. Run these in order and do not call it ready to merge until the chain is complete:
  1. `ship-check`, always, as soon as the PR/MR exists. It checks the change against the original ask and returns a merge / fix-first / reconsider verdict.
  2. UI changes: `persona-walkthrough` is required. `ship-check` runs it on a UI diff, together with `ui-audit` and `ux-audit`. If it did not run (no runnable app, ship-check skipped it), run it yourself. If it truly cannot run, say so in the PR/MR and keep it draft.
  3. `mr-review` when the diff is substantive: more than a trivial change, or it touches data, migrations, auth, money, shared code or concurrency, or `ship-check` did not return a clean "ship it". Skip it only for trivial diffs, and say that you skipped it and why. Do not infer readiness from green CI alone.
  4. `fix-review` whenever `ship-check` or `mr-review` left findings or open threads. Then rerun only the checks and gates the fixes affect.
  5. Right before the user merges: `mr-guide` where available, a skimmable page with before/after screenshots for UI changes. Merge only when CI and review are settled and the user has authorized merging. After merge, `spinoff` is optional for newly cheap follow-ups.
- Before asking the user anything, check the data you already have: the code, git log and blame, the issue and PR/MR threads, CI, test results, docs, your memory, and messages from other agents (`aw_inbox` under Agent Worlds). Whether something was deliberate, or whether a fix works, is checkable, so check it. Ask only what is still the user's call, give your recommendation and a one-line reason with each question, and split the list into "doing unless you say no" and "needs your yes" (commits, pushes, posting, filing issues).
- A goal that spans several repos or sessions and that the user wants run for them: `lead` in world mode, as the manager of the worker sessions.

Choose the applicable next step from the current state. Do not run planning gates retroactively on a finished change, or repeat a gate without a new change or unresolved concern. If a skill is unavailable or its tools cannot run, state that limitation and use the closest safe workflow. Never claim a skill ran merely because its name appeared in a summary.
