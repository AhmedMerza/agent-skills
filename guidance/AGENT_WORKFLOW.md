# Agent skill routing

Use the skills installed from `agent-skills` when the task reaches their trigger. Say which skill you are applying and why. The skill is a procedure to follow, not just a label to mention. Read its `SKILL.md` before acting. An explicit user request for a skill takes priority; do not force every task through the entire chain.

- Whenever you are about to ask the user to choose between approaches: `best-option` first. Explain each option, check for a better unlisted one, lead with your pick marked "(Recommended)", and say why the others lose.
- An unclear idea or problem with no route: `scout` to settle the destination and decisions. For a reported bug that needs diagnosis: `root-cause`. If a plan already exists and its assumptions matter: `validate-plan` before implementation.
- Product work: when anything end users touch is being planned, use `expand` in light mode on your own initiative (at most three ideas, offered at a boundary, never mid-implementation). Use full mode, with its own competitor research, at a product kickoff or milestone boundary. `scout` calls it for product destinations.
- A roadmap or multi-step plan is ready: `grill-me` with the user (scout and lead hand off to it at the roadmap gate), then `validate-plan` before filing issues or starting work.
- During implementation: `ponytail` for minimal, grounded code. When a new regression test matters: `prove-the-test`. For a changed UI flow, before committing: `qa-sweep` checks failures, and `persona-walkthrough` tests whether a first-time human can understand and finish the flow (when a runnable app is available).
- Once a PR/MR is open and the change is ready: `ship-check` checks completeness against the original ask. On a UI diff it also runs `ui-audit` and `ux-audit`, plus `persona-walkthrough` unless a walkthrough already covered this diff. Route those audits through ship-check rather than calling them separately. `mr-review` checks the diff line by line. Use both for a substantive merge, scaling effort to risk. Do not infer readiness from green CI alone.
- When review finds defects or threads need resolution: `fix-review`, then rerun affected checks and the relevant review gates. Right before the user merges: `mr-guide` where available, a skimmable page with before/after screenshots for UI changes. Merge only when CI and review are settled and the user has authorized merging. After merge, `spinoff` is optional for newly cheap follow-ups.
- A goal that spans several repos or sessions and that the user wants run for them: `lead` in world mode, as the manager of the worker sessions.

Choose the applicable next step from the current state. Do not run planning gates retroactively on a finished change, or repeat a gate without a new change or unresolved concern. If a skill is unavailable or its tools cannot run, state that limitation and use the closest safe workflow. Never claim a skill ran merely because its name appeared in a summary.
